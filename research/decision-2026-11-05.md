# text layer or browser layer, decision note

date: 2026-11-05

question: should quarry remove the browser layer and focus on the text layer, and is the text layer clearly better than the web tools in OpenCode, Claude Code, and Codex?

verdict: keep the text layer as the core, remove the open browser agent from the product, and keep replay and playbook memory only as an optional experiment. the text layer is useful, but it is not clearly far better overall. it is at accuracy parity or slightly behind, slower, and its token and cost advantage is not stable.

## measured comparison

10 documentation questions, 2 runs per arm, one model `opencode-go/glm-5.3-flash`, no supermemory, one tool arm per agent. raw data: `bench/agent/text-10.json`.

| arm | correct | wall, median | input tokens, median | cost, median |
| --- | --- | --- | --- | --- |
| quarry text MCP | 19/20 | 10.5 s | 6,713 | $0.00179 |
| OpenCode webfetch | 20/20 | 4.1 s | 9,511 | $0.00144 |

one quarry failure was a model turn that wrote a plan instead of calling the tool. the two earlier strict string checks were corrected after the first run. the sample is one model and ten questions. it is enough to reject a broad superiority claim. it is not enough to prove a general ranking.

## what the evidence supports

the text layer has a real niche:

- section retrieval on large docs, 5.75x median and 10.21x total on the selection sample
- a persistent cache with conditional revalidation
- batch fetch up to 20 URLs
- one research call that searches, fetches, and ranks sections

it does not have a general win:

- accuracy is 19/20 against 20/20, not a lead
- wall clock is 10.5 s against 4.1 s, a loss
- cost is $0.00179 against $0.00144, a loss in this sample
- input tokens are lower, 6,713 against 9,511, but the agent makes more turns, so the bill does not follow the token count

the browser layer has a different result:

- open browsing loses, 1/3 against 3/3 and 180 s against 20 s
- replay wins at 40/40, 1 token, and 1.8 s
- replay is a repeat-workflow feature, not a general browser

## recommendation

1. remove the open browser agent from the core product and stop claiming general browsing.
2. keep the text layer as the core: fetch, cache, outline, section, ask, batch, research.
3. keep replay and the local playbook store only if a repeat workflow exists. otherwise archive them.
4. do not claim the text layer is clearly better. claim the narrower win: section retrieval on large docs, with a cache and batch.
5. before any broader claim, run 50 questions across three models and compare against Claude Code WebFetch and Codex search. the current sample is 10 questions and one model.

## what would change the verdict

- if quarry wins accuracy and wall clock on 50 questions, the text layer can carry a stronger claim.
- if section retrieval does not beat full-page fetches on real agent tasks, the text layer is a cache and batch tool, not a retrieval product.
- if replay is not used repeatedly in real work, the browser folder should be archived.
