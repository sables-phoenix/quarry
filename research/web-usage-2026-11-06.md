## what this changes

the frequency is not zero. in this workspace, multi-URL work is common, and large-doc sessions are a real minority. 16% of web sessions touched a page over 100k chars. 68% used five or more URLs.

but the sample is biased. the workspace is research-heavy, and several sessions are our own quarry research. the titles include "Research local runner performance", "Research Cloudflare agent performance", "Research agent prior art speed", and "How web search and fetch work in OpenCode". a median coding agent doing a bug fix is not this user.

the usage data also shows no pull for the product:

- 0 sessions called quarry's section tools, because quarry was not installed in those sessions.
- the 10-question head-to-head showed 19/20 for quarry against 20/20 for webfetch, slower and more expensive.
- batch work is visible, but it is 5 to 10 sequential fetches, not a request for a batch API. the value of batch is fewer turns, not better content.

## decision

bin the standalone product thesis. do not build a separate web access layer for OpenCode users on this evidence.

keep a small internal section and cache tool only if this research-heavy workflow is the target. 16% of sessions touching a 100k page is enough to justify a personal utility, not enough to justify a product without a demand test.

bin the open browser agent. keep replay only if a repeat workflow is real.

if someone wants to reopen the product case, the next test is 100 real web tasks from at least five users, not one workspace. measure the same four numbers: pages over 100k, repeats within 15 minutes, five or more URLs, and section versus whole-page need.
